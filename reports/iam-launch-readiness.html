I AM / Web + mobile / Engineering assessment

Production readiness

Evidence snapshot: 17 October 2026. Scope: repository review, workspace type checks, security scanners, deployment metadata, public endpoint probes, and one isolated server-failure reproduction.

Decision: HOLD unrestricted public launch.

This is a real, professionally structured cross-platform application foundation, not a mock-only interface. It is not yet a verified production-grade multi-social platform. A restricted beta should follow—not bypass—the immediate security and release gates below.

1. What the evidence supports

  • Real shared infrastructure: Next.js web, Expo mobile, Express/Socket.IO API, Clerk identity, PostgreSQL social data, and private App Storage media.
  • Current workspace type checks passed: shared libraries, API, web, mobile, mockup sandbox, and scripts passed pnpm run typecheck during this assessment.
  • Recent unchanged-source build evidence: the immediately preceding verification passed the Next.js production build, API build, and four API tests. Those tests cover generated input validation, relational authorization/privacy, unsafe media metadata/signatures and push endpoints, and single-use owner/conversation-bound uploads. Four test cases do not mean every feature is covered.
  • Startup fix validated locally: the production web mount URL returned HTTP 200 without following redirects after the URL-canonicalization fix. This is not a successful republish.
  • Access-control protections found: parameterized database queries, authenticated social routes, transaction-based writes, per-member rate limits, blocking/privacy checks, and private media authorization. Uploaded files are verified and sealed before attachment.

No application source, dependencies, credentials, or deployment configuration were changed during this assessment. The server-failure test ran against a separate temporary local process, not the live service. No new signed-in browser or physical-device testing was performed.

Highest-priority dependency triage

  • proxy-addr 2.0.7: critical advisory, fixed version reported as 2.0.8; present through the Express API. The reported exploit needs a particular trusted-proxy IPv6 subnet misconfiguration. No such configuration was found in the inspected application. This is not a confirmed IP-spoofing exploit in I AM.
  • PostCSS 8.4.31: multiple high/moderate advisories in the Next.js dependency chain. Another newer direct PostCSS dependency does not remove this older transitive copy. Applicability depends on attacker-controlled CSS or source-map processing; an exposed untrusted-CSS processing feature was not found.
  • brace-expansion / braces: high denial-of-service advisories. Some copies are tooling-only; braces is also in the API proxy middleware dependency chain. Determine whether any untrusted pattern reaches those paths before judging exposure.
  • node-forge 1.4.0 and uuid 7.0.3: high advisories were traced to Expo CLI/config tooling. Their presence does not establish a flaw in the application's sign-in or message processing. The scan did not supply a fixed node-forge version; use upstream guidance rather than assuming a safe update exists.
  • source-map-js 1.2.1: high denial-of-service advisory; fixed version reported as 1.2.2. Review all transitive copies and whether untrusted maps are accepted.

Static flags that need precise review

serve.js:77 reads a manifest path formed from a platform value. Its caller whitelists ios/android, which substantially constrains the flagged input. serve.js:121 reads a static path; normalization and a prefix guard exist. The scanner flags merit containment tests and review, not an unsupported claim that arbitrary file disclosure has been demonstrated.

Privacy boundary

Private chats and media have server-side access controls. The reviewed implementation does not establish WhatsApp-style end-to-end encryption: message contents are handled and stored by the server. Do not market the app as end-to-end encrypted without a separate, verified cryptographic design.

5. Recommended work order

  1. Harden availability and triage security: fix the confirmed server exit, add malformed-input and path-containment regression checks, address applicable dependency advisories, and complete the privacy review.
  2. Choose a reliable beta topology: make an explicit always-running single-instance decision or add/test shared real-time coordination and durable worker scheduling. Do not claim scalable multi-instance messaging from an in-memory implementation.
  3. Close the release gate: publish after the above checks, then verify real published URLs, authentication, database compatibility and protected media. Do not bypass a failed health check.
  4. Complete device acceptance and promised launch features: separate-account web/iOS/Android testing, creator profiles, native video/calling/push if advertised, and permission/interruption/reconnection scenarios.
  5. Establish safety and operational ownership: moderation, data lifecycle, alerting, recovery drills, and performance targets measured against an agreed user/traffic budget.

Release rule: mark each gate “passed” only with reproducible evidence. No percentage-complete score or production certification is assigned; missing evidence is not a pass.

Platform guidance consulted: Replit deployment types. Reserved VM is intended for always-on workloads/persistent connections; Autoscale scales with requests and may scale to zero. Database persistence does not make process-local presence or call-room state durable.

This is a point-in-time engineering readiness assessment, not a penetration-test certification, legal compliance opinion, SLA, or guarantee of future uptime. No secrets or user records are included. Application hardening and publishing remain separate actions.
